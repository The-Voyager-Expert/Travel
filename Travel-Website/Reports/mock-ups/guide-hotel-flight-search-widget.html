4 · What it would actually cost to build

  • One block in toolbar.js, guarded by isRealGuide, appended to #ics-pill-row — structurally identical to the 💱 Currency block, including the terracotta “on” state and the iOS touchstart press shim.
  • No new data pipeline, no API key, no network call. City name comes from the guide slug the toolbar already resolves; the panel builds a URL and opens it.
  • New CSS lives in guide-style.css beside the .tve-cur-panel rules, reusing --c-warm-bg / --c-next-border / --c-card-bg so dark mode is free. The #bk-panel[hidden]{display:none} companion rule is mandatory — same [hidden] specificity trap the currency panel documents.
  • Inputs must be 16px or iOS Safari zooms the page on focus and throws the reader out of the guide — the constraint already written into .tve-cur-in.
  • Airport code is the one piece of per-guide data that does not exist yet. Either add an data-airport attribute on toolbar-mount, or ship Hotels only and drop the Flights tab.
  • The reader’s origin airport would sit in localStorage so it is typed once, not once per guide.

5 · Open questions for the owner

1 · Is a deep link worth a pill? The widget saves typing a city into Google, nothing more — no prices, no availability, no comparison. That is the honest ceiling of the feature.

2 · Six pills in the action row. The desktop row gets tighter and every pill loses width. Acceptable, or does something have to leave first?

3 · Flights tab in or out? It needs a new per-guide airport field on every shipped guide. Hotels-only ships with zero new data.

4 · Upcoming Trips strip — yes or no? Section 3 above; it is the only piece that adds a fetch and a coupling to Trips.html.

5 · Google, or a choice of provider? One button per tab is cleanest; two (Google + Booking) doubles the row height and starts to read as advertising.
